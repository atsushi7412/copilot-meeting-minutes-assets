# SSOTと議事録アセットの育て方

SSOTは、対象の正式名や関係を一か所で管理するための正本である。会議ごとの発言記録とは役割が異なる。runtime/SSOT-template.txtを複製し、5分類を一つのファイルで始める。

## 最初に登録する範囲

人物は正式氏名、読み、必要な識別情報、会社IDと組織IDを持つ。会社は法人単位、組織は会社の配下の部・課・チーム等の単位とする。製品とサービスは同じ分類内で区分を付ける。呼び方は正式データのIDへつなぐ対応辞書とする。

部署の名称だけで会社をまたいで同一視しない。人物の役職・所属、製品名や提供会社には有効期間を付ける。会議日時に有効なものを参照する。人物IDの同一性と、期間付きの所属関係は分けて管理する。候補として登録した新所属を、確認なしに確定所属へ昇格しない。

呼び方には、入力表記、対象ID、利用条件、出典、確認状態を持たせる。「佐藤さん」のような呼び方を複数候補へつなぐ場合、所属やアカウントで絞れなければ不明のまま残す。読みが近いだけで誤認識辞書へ追加しない。一意に照合できる根拠は、型番の完全一致、アカウント識別子の完全一致、SSOTに登録された語との表記一致の3種に限る。議論内容からの推論だけで対象を決める登録は避ける。

## 改善する場所を選ぶ

- 正式名・所属・呼称が違う：SSOTの情報、出典、有効期間を直す。
- 提案を決定にしてしまう：エージェントの作成手順（workflow部分）と、評価ケースを直す。
- 見出しや情報量が使いにくい：出力テンプレートと、指示中の出力指定を直す。
- 書き起こしや会議設定が足りない：入力の取得経路を直す。指示の追加で欠落を埋めようとしない。

## 更新の流れ

1. 出力の問題と、その根拠となる原文を記録する。
2. SSOT・指示・テンプレート・入力経路のどこに原因があるか選ぶ。
3. 正本を複製して開発用の変更を1点入れる。確認前の登録は「候補」にする。
4. 新しいチャットで同じケースを実行し、期待する改善が出るか比較する。
5. 他のケースも確認し、問題が増えていないか確かめる。
6. 管理者が確認後、業務用の版を更新する。旧版と変更理由を残す。
7. 参照先の反映と、実際に使われた版を確認する。下記「編集後の反映」の手順で再登録する。

会話で一度訂正しただけで、次の会議にも恒久的に学習されるとは扱わない。SSOTやエージェント指示の正本へ、確認した変更を反映する。

## 編集後の反映（再梱包・再登録）

SSOTの更新は、ナレッジに登録した業務用SSOTファイルそのものを編集して保存すれば反映される。版と更新日を書き換え、エージェントで新しい版を確認する（導入マニュアルの「業務用SSOTを登録する」参照）。再梱包は不要。

手順（workflow部分）や出力テンプレートを変更した場合は、利用方式によって反映方法が異なる。受講者はsource/tools配下にある保守者用の生成スクリプト（compiler・build・verify等）を使わない。それらは配布物の保守者が原本一式を作るための道具であり、受講者は以下の手動手順だけで自分のエージェントを再梱包・再登録する。

標準版（指示を貼り付けている場合）は次の手順で反映する。
1. 変更した指示の全文を用意する。agent-instructions.txtの構成に沿って、workflow部分または出力見出しの説明を編集する。
2. Agent Builderでエージェントを開き、構成画面の「指示／Instructions」欄の内容を、変更後の全文に置き換えて保存する。
3. 新しいチャットで対象ケースを実行し、変更前後の差を確認する。

スキル版（meeting-minutes-skill.zipを使っている場合）は次の手順で反映する。
1. 変更したSKILL.mdまたはoutput-template.txtを用意する。SKILL.md先頭のfrontmatter（name・description）は変更しない。
2. 元のZIPと同じ2ファイル（SKILL.md、output-template.txt）を、サブフォルダに入れずOS標準の圧縮機能でZIP直下へまとめて圧縮する。ZIPを開いた直後の階層にSKILL.mdが見える状態にする。
3. Agent Builderの構成画面でSkillsを開き、既存のmeeting-minutesスキルを削除してから、作成した新しいZIPを追加して保存する。古いZIPを残したまま重複登録しない。
4. 新しいチャットで対象ケースを実行し、スキルの説明・手順に変更が反映されているか、出力が変わったかを確認する。

どちらの方式でも、変更前後の出力・SSOTまたは指示の差分・残る不確実性を下記の変更記録のひな型に残す。全ケースの回帰確認は講師が実施する。

## 変更記録のひな型

変更日：／変更者：／対象版：／変更対象：
問題：／根拠の資料と発言位置：／原因の見立て：
変更内容：／変更前後の出力保存先：／期待事項：
回帰評価の結果：／確認者：／採用版：／取り消す場合の旧版：

## 研修演習

因果比較は、講師が配布する次の2ファイルで必ず行う。training/improvement/before/input-bundle.txt と、training/improvement/after/input-bundle.txt である。この2ファイルを使って、呼称対応の有無による出力の違いを必ず確認する。

受講者ZIPにはこの講師用ケースが入っていない。そのため、上記2ファイルは講師から別途受け取る。

beforeとafterは、同じ会議本文・同じ候補情報を使う。差は、対象範囲と有効期間の付いた呼称対応1件だけとする。版情報の差は管理用の差であって、因果には使わない。

実施手順は、新しいチャット・評価用エージェントで、旧版のナレッジや他ケースを外した状態にしたうえで、beforeとafterをそれぞれ実行して比較する。

期待される結果は次の2点である。beforeは対象が未確定のままとなる。afterは、追加した呼称IDを根拠として正規化される。曖昧な「佐藤さん」2名は、before・after双方で未確定のまま残す。

旧版のナレッジやケースが混入していたことが分かったrunは、INCOMPLETEとして扱い、清浄な因果比較には数えない。

旧来のように「C01相当の呼称対応を外す」手法は、因果比較に使わない。型番等から業務上正当に一意照合できる対応を禁止して見かけ上の変化を作ることは、効果の切り分けを損なうため行わない。

（注）本節の演習手順は文書上の整理であり、実機・人による校正は未実施である。
